# スペック駆動開発（SDD）の手順

> このリポジトリの開発フローです。**エージェントも人間も同じ手順に従います。**
> Claude Code では `/spec-new` `/spec-plan` `/spec-tasks` `/spec-check` で補助できます。他のエージェントを使う場合は、この文書の手順をそのまま実行してください。

## 基本原則

**spec なしで実装を始めない。** コードは spec から導かれる成果物であり、逆ではありません。

「とりあえず動くものを書いてから仕様を後付けする」を禁じる理由は、このリポジトリの過去の経緯そのものです。AI 採点が `Math.random()` のモックのまま「AI ○○点」と表示され続けたのは、仕様書には詳細な判定ルールがあったのに、実装がそこを参照せずに進んだためです。

## 5 つのフェーズ

```
[0] 正典確認 ──▶ [1] requirements ──▶ [2] design ──▶ [3] tasks ──▶ [4] 実装 ──▶ [5] 検証
                      │                    │             │
                   人間の承認          人間の承認     人間の承認
```

**各フェーズの移行時に人間の承認を取ります。** requirements を飛ばして design、design を飛ばして実装、は禁止です。

---

### [0] 正典を確認する

実装しようとしている機能が、製品仕様書（[docs/spec/](../spec/README.md)）のどこに定義されているかを特定します。

| 確認先 | 内容 |
| --- | --- |
| [docs/spec/](../spec/README.md) | 製品仕様書 v0.3。**これが正典**。機能 ID（AUTH / PRACTICE / STYLE / COMM / REN / HIST / NOTI）、画面 ID（U-xx / R-xx）、Entity 定義、権限表 |
| [docs/design/](../design/) | 横断的な実装設計。データモデル、Security Rules、Rule Engine、API 定義 |
| [docs/status/gap-analysis.md](../status/gap-analysis.md) | 現在の実装状況。何が未実装か |
| [docs/status/roadmap.md](../status/roadmap.md) | 優先順位、依存関係、未確定事項（TBD）の決定先 |

**正典に無い機能を作ろうとしている場合は、ここで止まって人間に確認します。** 勝手に仕様を発明しない。

> 仕様書 `docs/spec/` は Word 原本から生成した正典です。**直接編集しないでください**（[safety.md](safety.md) 参照）。

---

### [1] requirements — 何を作るか

`docs/specs/<NNN>-<feature-slug>/requirements.md` を作ります。

- `NNN` は 3 桁の連番（`001`, `002`, ...）
- 1 つの spec は**1 つのまとまった価値**を対象にします。イシュー 1 件よりは大きく、エピック 1 件よりは小さい粒度が扱いやすいです（例: 「カメラから手の高さ判定までを 1 本通す」= Prototype 1 相当）

書く内容:

| 項目 | 内容 |
| --- | --- |
| 目的 | この増分で何が可能になるか。ユーザー価値で書く |
| スコープ | 対象に含むもの |
| **スコープ外** | 含まないもの。**明示すること**（エージェントの探索範囲を狭める効果があります） |
| 受け入れ基準 | EARS 記法で書く（下記） |
| 前提・依存 | 先に完了している必要があるもの |
| 未確定事項 | この spec を書く時点で決まっていないこと。TBD-xx への参照 |

#### 受け入れ基準は EARS 記法で書く

曖昧な受け入れ基準はエージェントに都合よく解釈されます。次の型に当てはめてください。

| 型 | 書式 | 例 |
| --- | --- | --- |
| イベント駆動 | **WHEN** 〈条件〉**THEN** システムは〈応答〉**SHALL** | WHEN 手首が頭部基準より 0.05 以上上にある状態が 200ms 継続した THEN システムは GOOD イベントを発火する |
| 状態駆動 | **WHILE** 〈状態〉**THEN** システムは〈応答〉**SHALL** | WHILE 全身が検出できていない THEN システムは NOT_READY を表示し加点しない |
| 任意機能 | **WHERE** 〈機能が有効〉**THEN** システムは〈応答〉**SHALL** | WHERE コンボ機能が有効 THEN システムは連続成功数に応じてボーナスを加算する |
| 望ましくない事象 | **IF** 〈異常〉**THEN** システムは〈応答〉**SHALL** | IF カメラ権限が無い THEN システムは設定画面への案内を表示する |
| 常時 | システムは常に〈応答〉**SHALL** | システムは常に練習動画を visibility=private で作成する |

日本語で書いて構いません。**「適切に」「いい感じに」「必要に応じて」は使わない。** 検証できない基準は受け入れ基準ではありません。

→ ここで人間の承認を取る。

---

### [2] design — どう作るか

同じディレクトリに `design.md` を作ります。

| 項目 | 内容 |
| --- | --- |
| 方式 | 採用する実装方式。**選択肢を比較し、選んだ理由を書く** |
| 変更するファイル | 新規・変更するファイルの一覧 |
| データ変更 | Firestore / Storage の変更。[docs/design/data-model.md](../design/data-model.md) との整合 |
| 型・インターフェース | 主要な型定義、関数シグネチャ |
| テスト方針 | 何をどう検証するか |
| リスク | 失敗しうる点と対処 |

**横断設計（[docs/design/](../design/)）と重複する内容は書かず、リンクします。** 例: Rule Engine の状態機械は `docs/design/ai-basic-motion.md` にあるので、そこを参照して差分だけ書きます。

この spec で決めた事項が横断設計に影響する場合は、**`docs/design/` 側も更新します**（TBD の解決を含む）。決定が文書に残らないと、同じ議論を繰り返します。

→ ここで人間の承認を取る。

---

### [3] tasks — どう分解するか

同じディレクトリに `tasks.md` を作ります。

- 1 タスク = 1 コミットで完結する大きさ
- 依存順に並べる
- **既存の GitHub イシューと対応付ける**。このリポジトリには #5〜#59 のイシューがあります。新規に立てる前に既存を探してください
- 対応するイシューが無ければ、新規イシューの案として書く（起票は人間の承認後）

→ ここで人間の承認を取る。

---

### [4] 実装

- `tasks.md` の順に進めます
- タスクを 1 つ終えたら `tasks.md` のチェックを埋めます
- **spec から外れる必要が出たら、実装を進める前に spec を直します。** コードだけ変えて spec を置き去りにしない
- コーディング規約は [coding.md](coding.md)、禁止事項は [safety.md](safety.md)

---

### [5] 検証

[definition-of-done.md](definition-of-done.md) の全項目を満たしていることを確認します。満たしていない項目があれば、**満たしていないと報告します**。「たぶん大丈夫」で閉じない。

---

## ディレクトリ構成

```
docs/
├── spec/                        製品仕様書 v0.3（正典・直接編集禁止）
├── design/                      横断的な実装設計
├── status/                      実装状況・ロードマップ
├── rules/                       開発ルール（この文書を含む）
└── specs/                       ★ 機能単位の spec
    ├── TEMPLATE/                雛形
    └── 001-<feature-slug>/
        ├── requirements.md      何を作るか
        ├── design.md            どう作るか
        └── tasks.md             分解とイシュー対応
```

## Claude Code での補助コマンド

| コマンド | 対応フェーズ |
| --- | --- |
| `/spec-new <機能名>` | [1] requirements の雛形生成と対話 |
| `/spec-plan <spec番号>` | [2] design の作成 |
| `/spec-tasks <spec番号>` | [3] tasks の作成とイシュー対応付け |
| `/spec-check <spec番号>` | [5] 実装が spec を満たしているかの検査 |

他のエージェントを使う場合は、この文書の該当フェーズを読ませてください。**コマンドが無くても手順は同じです。**
