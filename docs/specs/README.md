# 機能単位の spec

> ⚠️ **既定はイシュー駆動です。ここに spec を作る必要は普段ありません。**
>
> イシュー #5〜#59 には受け入れ条件・仕様書該当箇所・設計文書へのリンクが入っており、**それが実質の spec** です。イシューを渡せば実装まで進みます（`/impl <番号>`）。

## spec を切るのはこの 3 つの場合だけ

| ケース | 例 |
| --- | --- |
| **A. 仕様書に無い機能を作る** | 「指導リクエスト」「1対1チャット」のように製品仕様書 v0.3 に定義が無いもの。何を作るかの合意が先に必要 |
| **B. 複数イシューをまたぐ判断が必要** | Prototype 1（#13〜#16）— TBD-01（姿勢推定の方式）を一度決めれば 4 イシューすべてが決まる。判断を 1 箇所に置きたい |
| **C. スコープの線引きに合意が必要** | 「どこまでやってどこからやらないか」が曖昧で、決めずに始めると手戻りする場合 |

**イシュー 1 件で完結する作業に spec は不要です。** 手順は [../rules/workflow.md](../rules/workflow.md) を参照してください。

## docs/spec/ との違い

| | `docs/spec/` | `docs/specs/`（ここ） |
| --- | --- | --- |
| 内容 | 製品仕様書 v0.3 全体 | 1 つの実装増分 |
| 位置づけ | **正典**（constitution 相当） | 正典から導いた作業単位の spec |
| 編集 | **禁止**（Word 原本を更新） | フェーズの承認を得て編集 |
| 粒度 | 製品全体 | イシュー数件ぶん |

紛らわしい名前ですが、**単数 `spec/` が正典、複数 `specs/` が作業単位**です。

## 構成

```
docs/specs/
├── README.md                     この文書
├── TEMPLATE/                     雛形
│   ├── requirements.md
│   ├── design.md
│   └── tasks.md
└── <NNN>-<feature-slug>/
    ├── requirements.md           何を作るか（受け入れ基準・スコープ外）
    ├── design.md                 どう作るか（方式の比較・変更ファイル）
    └── tasks.md                  分解とイシュー対応
```

`NNN` は 3 桁の連番、スラッグは英小文字とハイフンです。

## 粒度の目安

spec を切ると決めた場合、1 つの spec は**イシュー 3〜5 件ぶん**を対象にします。

| 粒度 | 例 | 判定 |
| --- | --- | --- |
| 大きすぎる | 「AI 解析機能をすべて」 | ✗ エピック #5 全体。肥大化して承認できない |
| ちょうどよい | 「カメラから手の高さ判定までを 1 本通す」 | ✓ Prototype 1 相当。イシュー 4 件ぶん |
| 小さすぎる | 「RULE-01 の閾値を定数に切り出す」 | ✗ イシュー 1 件で足りる。**spec は作らない** |

## 受け入れ基準は EARS 記法で書く

曖昧な受け入れ基準はエージェントに都合よく解釈されます。

| 型 | 書式 |
| --- | --- |
| イベント駆動 | **WHEN** 〈条件〉**THEN** システムは〈応答〉**SHALL** |
| 状態駆動 | **WHILE** 〈状態〉**THEN** システムは〈応答〉**SHALL** |
| 任意機能 | **WHERE** 〈機能が有効〉**THEN** システムは〈応答〉**SHALL** |
| 望ましくない事象 | **IF** 〈異常〉**THEN** システムは〈応答〉**SHALL** |
| 常時 | システムは常に〈応答〉**SHALL** |

日本語で書いて構いません。**「適切に」「いい感じに」「必要に応じて」は使わない。** 検証できない基準は受け入れ基準ではありません。
