# impl — イシュー駆動の実装

**このリポジトリの既定の実装フローです。** イシュー番号か URL を受け取って実装まで進めます。

イシュー #5〜#59 には受け入れ条件・仕様書該当箇所・設計文書へのリンクが入っており、**それが実質の spec** です。`docs/specs/` に別途 spec を切る必要はありません（必要な場合は `docs/rules/workflow.md` の 3 章）。

## 手順

### 1. イシューを読む

```bash
gh issue view <番号>
```

親エピック（`type:epic`、#5〜#12）が示されていれば、そちらも読んで**推奨着手順序と依存関係**を確認します。依存する他イシューが未完なら、**先にそれを指摘してください**（勝手に着手範囲を広げない）。

### 2. リンクされた文書を実際に読む

**リンクを読まずに書き始めないこと。** イシュー本文は要約であり、判断の根拠は設計文書にあります。

| 領域 | 読む文書 |
| --- | --- |
| データを扱う | `docs/design/data-model.md`（Firestore パス・フィールド・インデックス） |
| 権限・Rules | `docs/design/security-rules.md` |
| AI 採点（基本動作） | `docs/design/ai-basic-motion.md`（正規化式・状態機械・閾値） |
| スタイル類似度 | `docs/design/ai-style-similarity.md` |
| Cloud Functions | `docs/design/api-functions.md`（FN-01〜07） |
| 画面・遷移 | `docs/design/screens.md` |

仕様書（`docs/spec/`）の該当章がイシューに書かれていれば、そこも読みます。**仕様書に定義が無い機能を作ろうとしている場合は、止まってユーザーに確認してください。**

### 3. 現状のコードを読む

変更対象を実際に読みます。`docs/status/gap-analysis.md` の既知の不具合（B-1〜B-11）が触る範囲に含まれるなら、**併せて直すか別イシューに委ねるかを判断して報告**します。

### 4. 実装する

- コーディング規約: `docs/rules/coding.md`
- 禁止事項: `docs/rules/safety.md`（プロコン向けに絞ってあります。開発中に緩めてよいことも書いてあります）
- **既存コードが規約に反している場合は規約が正。** 既存コードを真似しない

イシューの受け入れ条件から外れる必要が出たら、**実装を進める前にイシューを直します**（`gh issue edit` の前にユーザーへ確認）。

### 5. TBD を決めたら記録する

未確定事項を決めた場合、**`docs/design/` の該当文書に決定内容と理由を書きます**。`docs/status/roadmap.md` の 4 章の状態も更新します。

イシューのコメントやチャットの中だけに残った決定は次の担当者に届きません。**これは省かないでください。**

### 6. 検証する

`docs/rules/definition-of-done.md` の項目を確認します。最低限:

```bash
cd Ren-kei_procon && npx tsc --noEmit
cd functions && npm run build          # Functions を変更した場合
```

イシューの受け入れ条件を 1 つずつ突き合わせます。詳しく検査するなら `/spec-check <番号>`。

### 7. 報告する

次を含めて報告します。

- 実装した内容（変更ファイル）
- **受け入れ条件のうち満たしたもの / 満たしていないもの**
- 実行した検証と結果
- 検証できなかったこと（実機が必要など）とその理由
- 決めた TBD と記録先

**満たしていない項目を隠さないこと。** 「たぶん動く」「概ね完了」で閉じない。テストが失敗したら失敗した事実と出力を貼ります。

## コミットについて

コミットは**ユーザーが求めたときだけ**行います。`main` にいる場合は先にブランチを切ります。

コミットメッセージは日本語で構いません。関連イシューがあれば `Closes #<番号>` を含めます。
