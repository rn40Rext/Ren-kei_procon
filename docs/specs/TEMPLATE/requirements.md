## 1. 目的

この増分で何が可能になるかを**ユーザー価値**で 2〜3 行で書く。技術的な達成ではなく、誰が何をできるようになるかを書く。

## 2. 背景・仕様書での位置づけ

製品仕様書のどこに定義されているかを示す。該当章へのリンクを入れる。

現状どうなっているか（`docs/status/gap-analysis.md` の該当箇所）も書く。

## 3. スコープ

含むもの:

- 箇条書きで列挙する

## 4. スコープ外

**必ず書く。** 含まないものを明示すると、エージェントの探索範囲が狭まり、意図しない変更が減る。

- 箇条書きで列挙する
- 「これは次の spec で扱う」と書けるなら、どの spec か示す

## 5. 受け入れ基準

EARS 記法で書く。**すべて検証可能であること。**

| ID | 基準 | 検証方法 |
| --- | --- | --- |
| AC-1 | WHEN 〈条件〉THEN システムは〈応答〉SHALL | ユニットテスト / 実機確認 / Emulator |
| AC-2 | WHILE 〈状態〉THEN システムは〈応答〉SHALL | |
| AC-3 | IF 〈異常〉THEN システムは〈応答〉SHALL | |

## 7. 未確定事項

この spec を書く時点で決まっていないこと。`docs/spec/17-open-items.md` の TBD-xx に対応するものは番号を書く。

| ID | 内容 | いつ誰が決めるか |
| --- | --- | --- |
| TBD-01 | 例: MediaPipe の RN 実行方式 | この spec の design フェーズで検証して決める |

**未確定事項が受け入れ基準に影響する場合は、requirements の承認時に人間へ確認する。**

## 8. 非対象の判断

「やらない」と決めたことと、その理由。後から「なぜやらなかったのか」を問われないために書く。
