# AI機能② 連スタイル類似度判定 実装設計

> 出典: [仕様書 8章 AI機能② 連スタイル類似度判定](../spec/08-ai-style-similarity.md) / [12.4 シーケンス](../spec/12-sequences.md)
> 付録C「Motion Encoder の技術選定結果・前処理・Embedding 次元・推論環境」に対応する文書です。

## 1. 目的と表現上の制約

ユーザーの動きが**どの連の熟練者の動きに近いか**を示す機能です。「上手い / 下手」の評価ではありません。

| してよい表現 | してはいけない表現 |
| --- | --- |
| 「あなたは ○○連 タイプ」 | 「87% の確率で ○○連」 |
| 「動きの類似度 82」 | 「○○連への適合度 A ランク」 |
| 「上位 3 連」 | 「あなたは ○○連 に向いていません」 |

確率表現を避けるのは、コサイン類似度が確率ではないためです（仕様書 8.5）。また特定の連への参加可否を示唆する表現は、コミュニティ運営上の問題になり得るため避けます。

## 2. 処理フロー

```
ユーザー動画 (Cloud Storage)
   │
   ▼
[1] 姿勢系列抽出（MediaPipe / 前処理は AI① と共通）
   │  landmark 時系列
   ▼
[2] Motion Encoder 推論           ← モデル未確定（TBD-08）
   │  Embedding U (固定次元 D)
   ▼
[3] 各連の代表 Embedding R_i と cosine 類似度を計算
   │  renStyleProfiles/{renId}.embeddingRef
   ▼
[4] 降順ソートし上位 N 件を保存
   │
   ▼
styleAnalysisResults/{id}   →  UI に「動きの類似度」として表示 → 連詳細 → 参加リクエスト
```

推論はバックエンド（Cloud Run 等）に置きます。モデルが重く、更新を一元化したいためです（仕様書 3.2）。

## 3. モデル選定（TBD-08 → 決定済み）

**決定: ベースライン特徴量エンコーダ `style-baseline-v1`（32 次元）を採用する。**
決定日 2026-09-04（イシュー [#22](../../../issues/22) の実装時）。
実装は [`functions/src/style/encoder.ts`](../../functions/src/style/encoder.ts)。

採用理由:

1. 連ごとの熟練者動画が現時点で 0 件で、大規模モデルを持ち込んでも評価すらできない。
2. 検証要件（8.6）の 2〜4（撮影距離・左右反転・再生速度）は特徴量の作り方で決まる。ここを満たせないうちは、より大きなモデルへ行っても同じ失敗を繰り返す。
3. 32 次元なら Firestore へ直接置ける（TBD-09 の判断が単純になる）。
4. 各次元の意味を説明できるため、順位の根拠をユーザーへ示せる。AI① の設計原則（説明可能性を最優先する）と揃う。

> **この決定は暫定です。** 実データで検証要件を満たせない場合は MotionBERT へ移行します。移行時は `StyleEncoder` インタフェースの実装を差し替え、`STYLE_EMBEDDING_VERSION` を上げます。**異なる版の Embedding を比較してはいけません**（6章）。

| Embedding 次元 | 関節ごとに 512 次元（frames × 17 × 512）。系列 1 本のベクトルにするにはプーリングを別途設計する必要がある | 潜在空間 256 次元 | 32 次元 |
| コードのライセンス | Apache-2.0 | MIT | 自作 |
| 重み・学習データ | 重みは Human3.6M / AMASS 等に由来し、コードとは別条件。**再配布・利用可否は要確認** | HumanML3D / AMASS と SMPL ボディモデルに依存。SMPL は非商用条件付き | 依存なし |

### ベースラインの 32 次元

すべて `bodyScale`（肩中心〜足首中心の距離）で正規化済みの量です。

| 次元 | 内容 |
| --- | --- |
| 0〜3 | 高いほうの手の高さ（平均 / 標準偏差 / 最大 / 最小） |
| 4〜7 | 低いほうの手の高さ（同上） |
| 8〜10 | 左右の手の高さの差（平均 / 標準偏差 / 95 パーセンタイル） |
| 11〜13 | 腰の高さ（平均 / 標準偏差 / 範囲） |
| 14〜16 | 膝角度の平均（平均 / 標準偏差 / 最小） |
| 17〜18 | 左右の膝角度の差（平均 / 標準偏差） |
| 19〜21 | 手首の速さ / 拍（平均 / 標準偏差 / 95 パーセンタイル） |
| 22〜23 | 腰の速さ / 拍（平均 / 標準偏差） |
| 24〜25 | 肩中心から手首までの水平距離（平均 / 最大） |
| 26〜27 | 足幅（平均 / 標準偏差） |
| 28 | 左右の手の高さの相関 |
| 29 | 手の上下移動量 / 拍 |
| 30 | 周期性の強さ（自己相関ピーク） |
| 31 | 手の速さ ÷ 腰の速さ |

### 不変性をどう作っているか

| 検証要件 | 実装上の対応 |
| --- | --- |
| 撮影距離（8.6-2） | すべての長さを `bodyScale` で割る |
| 左右反転（8.6-3） | 左右を `max` / `min` / 差の絶対値 / 相関など**対称な関数**で畳む |
| 再生速度（8.6-4） | 腰の上下動から自己相関でテンポ（Hz）を推定し、速度量を「1 拍あたり」に直す。**絶対テンポは次元に含めない**（含めると再生速度の違いで順位が動くため） |

> ⚠️ 標準化に使う中心値・スケール（`FEATURE_SPECS`）は、実データが無いため想定レンジから置いた**暫定値**です。実撮影データが集まったら平均・標準偏差で再推定してください（未決定事項）。定数を変えたら Embedding の意味が変わるため、**変更時は `STYLE_EMBEDDING_VERSION` も上げます**。

## 4. 代表 Embedding の作り方（仕様書 8.4）

連ごとに 1 名だけを基準にすると個人差が強く出ます。複数の熟練者・複数動画から代表表現を作ります。

```
R_i = (v_1 + v_2 + ... + v_n) / n        # 単純平均（プロトタイプはこれで可）
```

- `renStyleReferences` に個々の参照動画の Embedding を保存し、`approved == true` のものだけを代表計算に使います。
- 代表ベクトルは `renStyleProfiles/{renId}` に保存します。
- 参照追加・承認時に [FN-07 rebuildRenStyleProfile](api-functions.md#fn-07-rebuildrenstyleprofile) で再計算します。
- サンプル数 `sampleCount` を保存し、**サンプルが少ない連は UI で注記**します（例: 「参照データが少ないため参考値です」）。

### 正規化の注意

コサイン類似度を使うため、Embedding は L2 正規化しておきます。平均を取る前に各ベクトルを正規化し、平均後にもう一度正規化します。

```python
v = v / np.linalg.norm(v)          # 各サンプル
R = np.mean(vs, axis=0)
R = R / np.linalg.norm(R)          # 代表ベクトル
```

## 5. 類似度の算出と表示

```
cosine(U, R) = (U · R) / (||U|| * ||R||)      # -1 〜 1
```

表示値への変換方法は実験で決めます（TBD-10）。

| 案 | 変換 | 懸念 |
| --- | --- | --- |
| A | `round(cos * 100)` | 実データでは値が 0.9 台に密集し、連ごとの差が見えない可能性が高い |
| B | 検証データの分布で min-max 再スケーリング | 差が見えやすい。**推奨** |
| C | 順位のみ表示（数値を出さない） | 誤解が最も少ないが情報量が乏しい |

**推奨**: 上位 3 件を順位付きで表示し、数値は B の再スケーリング後の値を添える。1 位との差が小さい場合は「複数の連に近い傾向です」と表示して、順位の断定を避けます。

### 現在の実装（TBD-10 は未決定のまま）

実データの分布が無いため、B の再スケーリングに必要な min / max を決められません。暫定として **cos ∈ [0.5, 1.0] を 0〜100 へ線形写像**する定数を [`Ren-kei_procon/src/features/style/display.ts`](../../Ren-kei_procon/src/features/style/display.ts) の `DISPLAY_CALIBRATION` に置いています。

- 検証データが集まったら分布から min / max を再推定する。**この定数は表示専用**で、保存する `similarity` は生のコサイン類似度のまま（後から再スケーリングし直せるようにするため）。
- 1 位と 2 位の差が `CLOSE_MATCH_THRESHOLD`（0.02）以下なら「複数の連に近い傾向です」を表示し、順位を断定しない。
- `sampleCount` が 3 未満の連には「参照データが少ないため参考値です」を表示する。

## 6. データモデル

[data-model.md](data-model.md) の 2 章で確定したパスを使います。

| パス | 役割 |
| --- | --- |
| `renStyleReferences/{referenceId}` | 連ごとの参照動画とその Embedding（承認フラグ付き） |
| `renStyleProfiles/{renId}` | 連の代表 Embedding、`embeddingVersion`、`sampleCount` |
| `styleAnalysisResults/{id}` | ユーザーの診断結果（`results: [{ renId, similarity }]`） |

### Embedding の保存先（TBD-09）

| 次元 D | 保存方法 |
| --- | --- |
| D ≦ 512 | Firestore ドキュメントに `number[]` で直接保存（1MB 制限内） |
| D > 512、または連数が多い | Cloud Storage に `.npy` / JSON で保存し、Firestore には参照パスのみ持つ |
| 将来（連が数百規模） | ベクトル検索基盤（Vertex AI Vector Search 等）を検討 |

**決定（TBD-09）**: ベースラインが 32 次元のため **Firestore に直接保存**します（`embeddingRef: { kind: "inline", vector: number[] }`）。次元が大きくなったら `kind: "storage"` を足して切り替えられるよう、判別可能な形にしてあります。連が数百規模になるまでベクトル検索基盤は導入しません。

### 姿勢系列（landmark 時系列）の保存先

Embedding の再計算には元の landmark 時系列が必要です（版を上げたときに動画から作り直すのは高コスト）。そこで **姿勢系列を JSON で Storage に保存**し、Embedding はそこから何度でも作り直せるようにします。

| 用途 | パス | 参照元フィールド |
| --- | --- | --- |
| ユーザー動画 | `users/{uid}/videos/{videoId}.pose.json` | `videos/{videoId}.poseSeriesPath` |
| 連の参照動画 | `ren/{renId}/styleReferences/{referenceId}.pose.json` | `renStyleReferences/{id}.poseSeriesPath` |

形式は `{ formatVersion: "pose-series-v1", frames: [{ timestampMs, landmarks: [{x, y, z?, visibility}] }] }` です（`functions/src/style/pose.ts`）。

> 生成はクライアント側の MediaPipe パイプライン（AI①、[#13](../../../issues/13)〜[#14](../../../issues/14)）の担当で、**まだ実装されていません**。そのため現時点で FN-02 を実運用データに対して通すことはできません（7章）。

### バージョン整合

`embeddingVersion` が異なる Embedding 同士を比較してはいけません。比較時に必ず一致を確認し、不一致なら再計算します。

```ts
if (userEmbedding.version !== profile.embeddingVersion) {
  // 再推論が必要。STYLE_MODEL_UNAVAILABLE ではなく再計算キューへ
}
```

## 7. 検証計画と現在の状況（仕様書 8.6）

モデルを本機能へ統合する前に、以下を必ず測定します。**通らなければ機能を出しません。**

### 状況（2026-09-04 時点）

| # | 検証項目 | 合格基準（暫定） | 状況 |
| --- | --- | --- | --- |
| 1 | 同一人物の別テイクで同じ連が 1 位になる | 5 人 × 3 テイクで一致率 70% 以上 | ❌ **未実施**（実撮影データが無い） |
| 2 | 撮影距離の違いに影響されない | 近距離 / 遠距離で 1 位が変わらない | 🔶 合成データでのみ確認（cos = 1.00000） |
| 3 | 左右反転に影響されない | 反転前後で類似度差が 0.05 以内 | 🔶 合成データでのみ確認（cos = 1.00000） |
| 4 | 再生速度の違いに影響されない | ±20% の速度変化で 1 位が変わらない | 🔶 合成データでのみ確認（+20%: 0.99995 / -20%: 0.99990） |
| 5 | 連内個人差 < 連間差 | 連内のばらつきが連間距離より小さい | 🔶 合成データでのみ確認（連内 0.99980 / 連間 0.72192） |
| 6 | 熟練者の主観評価と乖離しない | 連関係者による評価とランキングが概ね一致 | ❌ **未実施**（連関係者の評価が必要） |
| 7 | 体格・撮影条件の類似になっていない | 同一人物が別の連の動きを真似たとき順位が変わる | ❌ **未実施**（実撮影データが必要） |

**7 が最重要です。** 体格や服装の類似を「踊りのスタイル」と誤認する失敗は起こりやすく、それに気づかないまま機能を出すと誤った案内をしてしまいます。同一人物が異なる連の動きを模倣した動画で順位が変化することを確認します。

### 合成データによる確認の位置づけ

2〜5 の 🔶 は、**合成した姿勢系列**（`functions/src/test/fixtures.ts`）による確認です。実撮影データの代わりにはなりません。合成データには MediaPipe の推定誤差・遮蔽・服装・背景がなく、連ごとの違いも人為的に作ったものだからです。

確認できるのは「エンコーダの設計上の不変性が意図どおり効いているか」までで、**「踊り方のスタイルを捉えているか」は確認できていません**。

```bash
cd functions && npm test            # 不変性テスト（エミュレータ不要）
cd functions && npm run verify:emulator   # FN-02/07/08/09 の動作確認
```

### 公開の可否

検証 1・6・7 が未実施のため、**UI はフラグで閉じています**（`STYLE_SIMILARITY_UI_ENABLED = false`、[`Ren-kei_procon/src/features/style/featureFlags.ts`](../../Ren-kei_procon/src/features/style/featureFlags.ts)）。実データで 1・6・7 を測定し、合格基準を満たしたときにフラグを開けます。満たせない場合は 9 章の縮退案 B へ切り替えます。

## 8. プライバシー上の注意（仕様書 14.3）

- 連スタイル参照動画は、提供者（熟練者本人）の同意と利用範囲を書面で明確化します。
- Embedding は元動画の代替的な個人情報となり得ます。アクセス制御（[security-rules.md](security-rules.md)）と削除方針を定めます。
- 参照動画の提供者が撤回を求めた場合、`renStyleReferences` の削除と `renStyleProfiles` の再計算をセットで行います。

## 9. 実装しない場合の代替（フォールバック）

検証が通らない、または期間内に間に合わない場合の縮退案です。

| 案 | 内容 |
| --- | --- |
| A | 機能自体を出さず、連検索（U-07）のみ提供する |
| B | AI① の項目別スコアの傾向（手が高い / 腰が低い等）で連の特徴とマッチングする簡易版にする |
| C | 連側が自己申告した特徴タグ（`beginnerFriendly` 等）でのフィルタに置き換える |

**B は AI① の実装だけで実現でき、説明可能性も高い**ため、現実的な縮退先です。機能を落とすより、根拠を説明できる簡易版を出すほうがユーザーにとって有益です。
